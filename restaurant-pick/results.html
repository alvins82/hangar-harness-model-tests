Restaurant Pick / Results

Second task in this repository, over the same models as the hangar test. Plan dinner for two in Sydney on a fixed Saturday against a fixed taste profile, verify every recommendation against the venue's real booking system rather than its opening hours, and answer a question about one named venue whose booking platform blocks automated checks. Prompt in PROMPT.md, scoring in RUBRIC.md, per-run table in index.html.

There are two separate axes here, and conflating them is the easiest way to read this table wrong. Speed and cost are extracted from the transcripts and are not matters of opinion. Quality of recommendation is a scored judgement — and on this task a fast, cheap, confident answer can be worthless, because a fabricated recommendation renders exactly like a checked one.

Reasoning share is reasoning tokens as a proportion of generated output, and it is the main cost driver: output is priced 3–5× input on every model here. A partial duration means the process was killed by a harness timeout rather than finishing; where a deliverable was still produced the output is complete even though the run is not.

The Opus baseline row is estimated, and marked ~like this. That run happened in a Claude Code session rather than through a harness, so there is no transcript carrying usage. What the estimates rest on: tool calls ~48 is the number of underlying HTTP requests, counted from the scripts it actually ran (12 SevenRooms slug probes, 4 availability queries, 4 venue-identity page loads, 2 OpenTable routes, 16 Google Maps lookups, 8 searches and fetches) — its ~20 direct tool calls understate the work badly, because each browser script batched several venues into one call, which is not how the OpenRouter rows count. Duration ~15m is inferred from roughly eight Chromium launches with their navigation waits plus the search round trips, and has the widest error bar of anything here; treat it as an order of magnitude. Tokens are inferred from about fifteen turns of accumulating tool output, with the 12 KB deliverable accounting for ~3,400 of the output figure. Cost is deliberately blank: Opus 5 is not on the OpenRouter rate card this table prices everything else with, so a dollar figure would invite exactly the false comparison the rest of this page is trying to avoid. Do not rank this row against the measured ones on speed or cost. Its quality score and its verification work are the parts worth reading.

1b. What it cost, and what I said it would cost the number that matters

Two things belong here. What the baseline actually cost, since it is the only row priced on a different rate card and the comparison is the whole point of running a benchmark. And how badly the up-front estimate missed, because that turned out to be the most useful finding of the exercise.

The baseline’s cost, estimated

Opus 5 is $5.00 per million input tokens and $25.00 per million output, with cache reads at roughly a tenth of the input rate. Against the estimated ~185,000 input and ~20,000 output tokens, and the 70% cache-hit rate the measured OpenRouter runs actually showed:

No caching$1.43upper bound

Which makes the baseline the wrong answer on cost as well as on blindness. Qwen 3.8 27B scored 91 at $0.64. The Opus baseline scored 81 at roughly $0.84 — more money for a lower score, against a rubric it wrote itself. And Luna scored 63 at $0.0072, which is 117× cheaper than the baseline for an answer that is worse but not 117× worse. On this task the frontier model is not the rational choice; the cheap reasoner that actually attempts verification is.

Wrong by up to 21×, in both directions, on the same task. The estimates assumed every model would consume comparable tokens, because the prompt and the tool surface are identical. Measured input ranged from 26,283 to 1,553,115 — a 59× spread. The cost of an agentic run is set by how many turns the model takes and how much it re-reads, which is model behaviour, not task size — so a per-model forecast derived from the task is close to worthless. Forecast a budget cap and let the run stop against it, which is what --max-cost now does; do not forecast a price.

Hard filters

  • Google rating 4.4+, with review count and source
  • Independent only — no chains or groups
  • Open at 7pm that night, hours sourced
  • ≤45 min drive, drive time stated
  • $100–150 for two, excluding drinks

Taste

  • A clear, specific identity
  • Share plates as the format
  • Italian, Korean, Middle Eastern, Chinese, Vietnamese or Thai lean
  • New openings and places getting press
  • Avoid: hotel restaurants, view-led dining, generic mod-Aus, wine-bar-first, chains

The actual test

  • Query the real booking system per venue — hours prove nothing about a table
  • Verify a venue’s identity before trusting its booking slug
  • Never infer availability from opening hours
  • One named venue’s platform blocks automated checks — say so, don’t claim a table

Scoring, /100

  • Verification 40 · Filters 20 · Taste 15
  • Honesty 15 · Named venue 5 · Output 5
  • Marked twice — write-up and transcript. The transcript wins.
  • Verification’s 8-point “result matches the transcript” line is awarded in proportion to what the transcript records: full where tool bodies are on record, half where only calls are, zero where there is no machine transcript

The thing to notice. Only the Opus baseline confirmed an actual 7:00pm table — and it is the one run that cannot be trusted as a result, because it wrote the prompt and scored itself. Of the three blind runs, Qwen found the 7:00pm seat at its best venue was waitlist-only and said so; SOL and Luna confirmed no table anywhere and hedged every option. Nobody except Qwen and the baseline actually produced a bookable 7pm dinner, which is the brief.

3. The one quality finding that is not a judgement call

PROMPT.md states that OpenTable blocks automated availability checks. Qwen was the only run that attempted OpenTable (opentable.com.au/r/lopresti-s) before reporting it blocked. Luna and SOL both assert the block in their write-ups with zero OpenTable requests anywhere in their transcripts. That is checkable from the transcripts rather than scored, and it means the pre-documented platform notes in the prompt can be read back as a finding. Two of three runs did exactly that.

Set against that, the best verification behaviour observed came from Qwen, which distinguished SevenRooms type:"book" from type:"request" without being told to, and rather than claim a 7:00pm table reported one venue as bookable 17:30–18:15 with the 19:00 seat waitlist-only. An honest negative, volunteered.

4. Recommendations

  1. Move the platform notes out of the prompt. Put the SevenRooms, NowBookIt and OpenTable specifics in a separate hints file the model has to ask for, or drop the OpenTable verdict entirely and let the block be discovered. As written, the task rewards reading comprehension over verification, and two of three runs collected that reward. This changes what the benchmark measures, so it is a design decision rather than a bug fix.
  2. Cap runs by cost, not wall clock. A 1500s timeout killed the first GLM attempt four seconds short of finishing, and 2400s cut Qwen off after it had written its deliverable. Both wasted spend and produced partial rows. The cost cap already exists; leave the time limit as a generous backstop only.
  3. Astra is the weakest use of the next $8. These runs separate on whether a model attempts verification, not on raw capability — Luna scored the same as SOL at a tenth of the cost. If matrix completeness matters, fund it properly first so a single run cannot strand mid-flight, rather than expecting it to top the table.
  4. Re-run Qwen and Luna now that tool bodies are recorded. They are the two most interesting rows and neither is auditable, which defeats the point of a task about honesty. Roughly $0.65 to fix.
  5. Judge these three write-ups yourself before trusting the scores. Speed is settled; quality is not. The specific calls to check are in the row under each result — whether blanket hedging counts as honest or evasive, and whether offering four options instead of three is a fault.
  6. Two fixes for the hangar table itself. Its OMP rows carry data-sort in milliseconds while every other row is in seconds, so they sort to the extreme of the Duration column. And the published OMP durations are not reproducible from the transcripts because those sessions were resumed — one spans 33 hours of wall clock.

One number per cell. Where a judgement was contested it has been made and the reasoning is in the row beneath, rather than published as a range — a score that hedges between two totals is not a score. Section 3 (verification) is earned / applicable × 40, with lines that cannot apply to a run dropped from the divisor rather than counted as failures.
