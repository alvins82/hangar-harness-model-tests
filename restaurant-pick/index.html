Same matrix as the hangar test, different failure mode. The hangar prompt asks a model to build something, and you can judge the result by opening it. This one asks a model to confirm something, where a fabricated answer and a checked answer look identical on the page — so every run is scored against a fixed rubric and cross-checked against its own transcript.

Prompt: Plan dinner for two in Sydney on a given Saturday against a fixed taste profile, verify every recommendation against the venue’s real booking system rather than its opening hours, answer a named-venue question whose booking platform blocks automated checks, and output one self-contained HTML file. The first row is a baseline, and it is not a blind run: that model wrote the prompt and the rubric and then scored itself, so it is a shakedown of the scoring sheet rather than a comparable result. It also ran outside the four harnesses, so it has no transcript in a format the extractor reads and no token or cost figures. Its two scores are the same run marked leniently and strictly — the spread is the starred pick sitting on the water at the new Sydney Fish Market, which is arguably the “view is the point” hard avoid.

What the first three OpenRouter runs found. The prompt states that OpenTable blocks automated checks. Qwen was the only run that attempted OpenTable before reporting it blocked; Luna and SOL both asserted the block with zero OpenTable requests in their transcripts, which is the pre-documented platform pack being read back as a finding rather than verified. That costs them the blocked-check line and an honesty deduction. SOL is the only fully auditable run — every quoted rating and phone number traces to a real tool result — and also the run that confirmed the least: two slug probes returned nothing and its write-up contains no bookable verdict at all. Qwen distinguished SevenRooms type:"book" from type:"request" unprompted and reported a 7:00pm seat as waitlist-only rather than claiming a table. Review counts are obtainable: Qwen quoted 580 and 648, SOL quoted 112.

The remaining rows are seeded with the matrix and marked Pending. Fill one by dropping its transcript and recommendation.html into the matching directory, then running ./extract_metrics.py <run-dir> --model <key> --harness <name> --row and pasting the result, which arrives with the three hand-scored cells empty. Score, Fabrications and Booking checks come from score.json, scored by hand against RUBRIC.md — Score out of 100, Fabrications the count of invented venues, ratings, links or times, and Booking checks how many recommended venues had a booking system actually queried over how many were recommended.

Token and cost columns use the same definitions and OpenRouter rates as the hangar table. extract_metrics.py reproduces the published hangar figures for input, output, reasoning and total tokens, cached input % and all four cost columns, on all ten rows across all four transcript formats — test_extract_metrics.py pins every one of those cells. Duration, TTFT, Tool calls and Tool errors are computed to one stated definition per harness and match the hand-counted hangar values on 7, 2, 8 and 6 of ten rows respectively; the README has a table of exactly where and why each differs.
