Restaurant Pick / Model Tests

Same matrix as the hangar test, different failure mode. The hangar prompt asks a model to build something, and you can judge the result by opening it. This one asks a model to find out something, where a fabricated answer and a researched answer look identical on the page — so every run is scored against a fixed rubric and cross-checked against its own transcript.

Prompt: Plan dinner for two in Sydney on Saturday 26 September 2026 at 7:00pm against a fixed taste profile, verify every recommendation against the venue’s real booking system rather than its opening hours, answer a named-venue question whose booking platform blocks automated checks, and output one self-contained HTML file. Rows are seeded with the matrix and marked Pending until a run lands. Fill one by dropping its transcript and recommendation.html into the matching directory, then running ./extract_metrics.py <run-dir> --model <key> --harness <name> --row and pasting the result. Score, Fabrications and Booking checks come from score.json, which is scored by hand against RUBRIC.md — Score is out of 100, Fabrications is the count of invented venues, ratings, links or times, and Booking checks is how many recommended venues were verified against a real booking system out of how many were recommended.

Token and cost columns use the same definitions and the same OpenRouter rates as the hangar table, and extract_metrics.py reproduces all ten published hangar rows exactly — see test_extract_metrics.py. Duration, TTFT, Tool calls and Tool errors are computed from the transcript to one stated definition per harness, which can differ slightly from the hand-counted values on the hangar table; the note in the README says where.
